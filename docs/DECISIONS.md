# Technology Decisions

Each choice lists why it was made and what was rejected. Add a row whenever you make a real choice;
this file feeds the "choices and trade-offs" sections of the Part A document.

| Area | Choice | Why | Rejected and why |
|---|---|---|---|
| Build tool | **Vite** | Fast dev server, simple config, standard for React + TS. | Next.js: server rendering adds nothing to a client-only 3D micro-app. CRA: unmaintained. |
| 3D | **React Three Fiber + drei** | three.js underneath (largest ecosystem, glTF/Meshopt/KTX2 loaders), but the scene is React components that read the same store as the panels. drei gives `Grid`, `OrbitControls`, `Stats`, `useGLTF`. | Plain three.js: works, but syncing an imperative scene with React panels means hand-written glue. Babylon.js: strong engine, but a heavier bundle and a separate mental model from React. |
| State | **Zustand** | Small, no boilerplate, works outside React (R3F render loop, tests). Selectors avoid re-rendering the canvas on unrelated changes. | Redux Toolkit: more ceremony than a single-screen editor needs. React Context: re-renders every consumer on each change; too slow during drags. |
| Undo/redo | **Command pattern, commands as plain data** (`applyCommand` + `invertCommand`), history capped at 200 | Each edit is small and explicit; history memory grows with edits, not with scene size. Data (not closures) can be serialised: the same commands can go to the server, and an assistant can propose them as JSON that is validated, previewed and applied as one `batch`. | Snapshot stack (store whole state per edit): simplest, but memory grows with items × history length. Command objects with `do()`/`undo()` methods: can't be serialised. Immer patches: good, but less readable to explain. Unlimited history: grows without bound in an all-day session. |
| Snapping | **Snap the footprint edge, clamp at walls, enforce in the store**; rotate about a fixed pivot with a ±half-cell shift | One formula handles odd and even footprints. Enforcing in the store makes "always on grid, always inside" an invariant for every caller. The alternating shift keeps 2×1 items aligned without drifting. | Snap the centre: odd footprints land half a cell off. Always re-snap after rotating: ties break the same way, so the item drifts 0.25 m per turn. Rotate about a corner: no drift but the item visibly jumps. Restrict catalog parity: arbitrary limit. Reject out-of-floor moves: drags past the wall do nothing. |
| Rendering | **One `InstancedMesh` per item type from the start** (capacity 2,000) | 3 draw calls for any number of items, the final design for the 500-item test, so no rewrite later. Clicks map `instanceId` → item through `groupItemsByType`. Bounding sphere recomputed after each update (three.js caches it; stale spheres break clicks and culling). | One `<mesh>` per item first: easier for an hour, but 500 items = 500 draw calls and selection would be rewritten when switching. |
| Selection highlight | **Thick outline** (drei `Edges`, 3 px) around the selected item | Keeps colour free for rule violations (red), so "selected" and "violating" never hide each other. One extra draw call. | Recolouring the selected item: clashes with violation colours. |
| Placement preview | **Local state in `Floor`**, updated only when the snapped cell changes | Changes many times a second; must never reach the store or undo history. | Storing hover in Zustand: needless global updates and re-renders. |
| Dragging | **Live drag position in the store (`drag`), not in history**; one `moveItem` on release | The item itself moves (the ghost is reserved for placing). 3D view and outline both read `drag`; the clearance rule can use it for live warnings. Updates only when the snapped cell changes. Esc cancels. | Moving the real item through commands on every cell: floods history. Ghost while dragging: confusing next to the placement ghost, no live rule feedback. |
| Drag geometry | **Infinite plane at floor height + grab offset**; camera controls off during a drag | Plane keeps the drag working over other items and past the floor edge. The offset keeps the cursor on the part of the item that was grabbed. | Ray-casting against the floor mesh: drag stops when the pointer leaves the floor or passes over an item. |
| Shortcuts | **Pure `shortcutFor(event)` + one global listener**; Ctrl and Cmd equivalent; Ctrl+Y also redoes; ignored while typing | The key mapping is unit-tested without a browser; Windows users (the brief's laptops) expect Ctrl+Y. | Per-component listeners: scattered, easy to double-fire. A shortcut library: extra dependency for five keys. |
| Item list ↔ 3D sync | **One `selectedId` in the store, read by both**; the selected row scrolls into view with `scrollIntoView({ block: 'nearest' })` | No sync code: both sides read the same value, so they can't disagree. `nearest` only scrolls when the row is hidden. Rows are plain buttons with `aria-current`. | Keeping a separate "list selection": two sources of truth. Virtualising the list now: 500 rows is fine for React; worth it at 10,000 (Part C). |
| Item names | **Derived, read-only** (translated type + number) | Nothing extra in history; switching language renames every item, including in rule messages. | Editable names: a new `rename` command, and a custom name doesn't translate. |
| Properties editing | **Text field, applied on Enter / leaving the field**; accepts `3.5` and `3,5`; rotation as a 0/90/180/270° dropdown | One edit = one undo step (not one per keystroke). Values go through `moveItem` / `rotateItem`, so they snap like a drag. Shows numbers in the chosen language's format, not the browser's. | `<input type="number">`: the browser picks the decimal format, ignoring our EN/VI toggle. Applying on every keystroke: floods history and snaps half-typed values. Rotate button only: 0° → 270° needs three clicks. |
| Clearance rule | **Pure `findViolations(items)`, every pair, true shortest edge-to-edge distance** | Simple to read and test. The brief's cases (touching, 0.59, 0.6, rotated) are unit tests. Measured ~1.4 ms for the 500-item test layout (124,750 pairs, 3,783 violations) on an Apple M4 (`npm run bench`), far inside a 16 ms frame, so no spatial index yet. Quick exit when one axis gap is already ≥ 0.6 m. | Largest-axis gap: flags diagonal neighbours 0.71 m apart, not a real distance. Spatial grid now: more code, no measured need at 500; it is the answer for 10,000 (Part C). Centre-to-centre distance: lets large items overlap unflagged. |
| Violations in the app | **Derived by a cached selector** (`selectViolations`), using the live drag position | Never stored, so undo/redo can't get out of step. Cached on the `items` and `drag` objects, so the 3D view, list and panel share one computation, and items turn red during a drag before anything is recorded. | Storing violations in the store: a second source of truth to keep in sync. `useMemo` in each component: the rule would run three times per change. Checking only after drop: no live feedback. |
| Violation highlight | **Whole item red via per-instance colour**; ⚠ on list rows; messages in a "Clearance" panel | Zero extra draw calls however many items violate. Material is white, instance colour carries the type colour or red. Selection keeps its yellow outline on top. Only the summary line is `aria-live`, so screen readers aren't flooded during a drag. Messages capped at 50. | Red outline per item: one extra draw call per violating item. Announcing every message: noisy. |
| Message templates | **`{name}` placeholders in `translate()`** + `Intl.PluralRules` for counts | "Cabinet 2 and Drive 5 are 0.5 m apart" has a different word order in each language, so sentences can't be glued together in code. A missing value stays visible as `{a}` instead of silently blank. | String concatenation: breaks word order in other languages. ICU MessageFormat library: right for the full product, overkill here. |
| Keyboard moves | **Arrow keys move the selected item along fixed floor axes**, 0.5 m (Shift: 2 m), one undo step per press; work anywhere except text fields and the list | Predictable whatever the camera does, and matches the "x, z" read out and shown in the properties panel. Goes through the same store helpers, so snapping, walls, overlaps and undo behave exactly like a drag. | Camera-relative arrows: more natural after orbiting, but the same key moves differently by view, which is hard for screen-reader users. Merging a burst of presses into one undo step: extra store logic. Arrows only when the 3D view has focus: an extra Tab every time. |
| Keyboard selection | **Placed-items list as an ARIA listbox**: one Tab stop, ↑/↓/Home/End, `aria-activedescendant` | 500 rows would otherwise be 500 Tab stops. The standard pattern screen readers know. | One button per row (the first version): fine with a mouse, unusable with a keyboard at 500 items. Tab cycling through items inside the 3D view: traps Tab. |
| Screen-reader announcements | **One hidden `aria-live` region; the sentence is built from the command** (`describeCommand`), stored as data (`announcement`) and translated when shown | Mouse, keyboard, list and undo/redo all produce commands, so every edit is described the same way, in the current language, from one tested function. The 3D view is `role="application"` with a help text, so screen readers pass the arrow keys through. | Announcing from each component: easy to miss a path (undo, drag) and to word the same edit differently. Storing the translated sentence: wrong language after a switch. |
| Shortcut help | **Native `<dialog>` (modal), opened by itself on the first visit only** (remembered in `localStorage`), then from a header button or the `?` key | The browser handles focus trapping, Esc and returning focus, and screen readers announce it as a dialog. First visit only: new users find the shortcuts, daily users aren't interrupted. Editor shortcuts pause while it's open, so Esc closes it without clearing the selection. A short CSS-only fade/scale (ease-out 0.22 s opening, ease-in 0.15 s closing, off for "reduce motion") keeps the native dialog behaviour. | Opening on every load: annoying for regular users. A non-blocking corner card: harder to reach and dismiss with a keyboard or screen reader. A hand-made modal: focus trapping and Esc are easy to get wrong. |
| Overlaps | **Refused in the store helpers**, for every edit (place, drag, rotate, properties); a toast names the item in the way | One check covers every way of editing, like snapping. Undo/redo need no check: they only revisit states that were already free. While placing, the ghost turns red first, so the user rarely gets refused. | Allowing overlap and flagging it (the first version): the user asked for overlaps to be impossible. Checking in each UI component: easy to miss one path. |
| Drag over an occupied cell | **The item stays at its last free cell**; the warning pops up again for each occupied cell; release drops it there | The user's choice: the drag is never lost, and the item never sits on another one, even for a moment. | Snapping back to the start on release: loses the whole drag. Showing the item overlapping in red until release: the layout looks invalid mid-drag. |
| Refusal message | **Toast over the 3D view**, 3 s, `role="alert"`, stored as data (`notice`: message key + item) | Visible where the user is looking; doesn't interrupt placing many items; translated at display time, so switching language mid-toast works. `pointer-events: none`, so it never blocks a click. | Modal dialog: must be closed every time, annoying when placing many items. Storing the translated text: wrong language after a switch. |
| Bill of materials | **Pure `billOfMaterials(items)` + a `<table>`**: item, size W × D × H, quantity, total; only types in use, in catalog order | Counted from the items on every change (`useMemo`), never stored, so edits, undo and redo can't make it wrong. A real table (`th scope`, `tfoot`) reads correctly in screen readers. Sizes and counts use the language's number format. | Storing counts and updating them on each command: a second source of truth. Listing types with quantity 0: noise in a parts list. Part numbers / prices: not in the brief, and inventing them would be fake data. |
| Stress test | **`?seed=N` + pure `seedLayout(count)`, loaded with `loadLayout`** (not undoable) | Same layout every time, so runs compare. Shelf packing (transformers first, then cabinets and drives in rows) fits 500 with no overlaps; tests check grid, floor and overlaps. `loadLayout` is also what the embedded mode will use to open a project. | A "Fill 500" button: a test tool inside the product UI. Random placement: different every run, and may not reach 500 without overlaps. |
| Measuring FPS | **Scripted real-Chrome run (Playwright, GPU) + `?stats` overlay with draw calls**; frame times, main-thread time, and a vsync-off run | 60 Hz caps FPS at 60, which hides headroom: main-thread time per frame and the uncapped FPS show it. Scripted runs repeat exactly. The overlay writes to the DOM directly, so measuring doesn't cause React re-renders. | Watching the counter only: no headroom figure, hard to repeat. Headless software rendering: measures the CPU rasteriser, not the GPU. |
| Model to optimise | **Khronos Flight Helmet** (48 MB, CC0), on a separate benchmark page | Suggested by the brief, clear licence, several meshes and big PBR textures like a CAD export. Kept out of the editor so the measured editor stays the same. | An industrial model from Sketchfab: licences vary and downloads need a login. Using it as an editor item: a helmet as a transformer looks odd, and it changes the measured editor. |
| Geometry compression | **Meshopt**, not Draco (both measured) | Draco makes this file only 2% smaller (geometry is 0.45 MB of 3.4 MB) but needs a 204 KB decoder, so it loads ~0.08 s slower at 10 Mbps; it also decodes more slowly and drei fetches its decoder from a Google CDN by default. Meshopt's decoder is a few KB, bundled. | Draco: right when geometry dominates (a big CAD mesh with few textures); the table in OPTIMISATION.md shows when it would win. |
| Texture compression | **KTX2: ETC1S for colour and occlusion/roughness/metal, UASTC + Zstandard for normal maps**; 1024 px (512 px normal maps) | KTX2 stays compressed on the GPU: 285 MB → 8.7 MB texture memory. UASTC only where block artefacts would show. | WebP: smaller downloads but full size on the GPU. UASTC everywhere: 6.29 MB file. Under 1 MB: needs 256 px textures or poor normal maps, a visible loss. |
| Pipeline tooling | **`@gltf-transform/cli` as a dev dependency, one step per command in `scripts/model-optimise.mjs`; KTX-Software unpacked into `.tools/`** | Each step's size is printed, so its effect can be explained. The pinned version makes the result repeatable. KTX-Software has no Homebrew package and its `.pkg` needs admin rights, so it is unpacked locally (the script falls back to WebP without it). | The single `gltf-transform optimize` command: one opaque step, harder to explain and tune. |
| Benchmark page | **Settings in the address, every change is a new page load** | Each measurement starts cold, like a user opening the editor, and a script can open any setting directly. | Toggling inside one page: models stay in memory and the GPU cache, so load times would be wrong. |
| i18n | **Typed dictionary + `Intl`** | Two languages and a few dozen strings; `Record<MessageKey, string>` makes a missing translation a compile error; `Intl.NumberFormat` handles locale numbers. Zero dependencies. | i18next / FormatJS: the right call for the full enterprise app (plurals, ICU messages, lazy-loaded namespaces) and named as such in Part A, but extra moving parts here. |
| Testing | **Vitest** | Same config as Vite, fast, Jest-compatible API. Logic in `domain`/`rules`/`commands` is tested without a browser. | Jest: needs separate transform config. |
| Lint | **oxlint** (Vite default) | Fast, zero config. | ESLint: more rules but more setup; not needed for this size. |
